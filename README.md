# 决策透镜（decision-lens）

面对模糊、高杠杆、多约束、长期影响的难题时，先用认知透镜重构问题再下判断。

你拿不准一件事时，缺的往往不是更多信息，而是**看这件事的角度**。本技能从 42 张透镜里挑出 1 到 3 个真正能改变你决定的，逼你把「打算怎么做 → 改成怎么做」写出来，再告诉你下一步交给谁。

**只挑 1-3 个，不是把 42 个都过一遍。**

---

## 什么时候用

- 你拿不准，而且隐约觉得自己可能问错了问题
- 一个决策错了要返工，影响面不小
- 有两个以上互相冲突的目标，需要决定让哪一头
- 结论会被反复引用，不是一次性的

## 什么时候别用

- 纯执行型、无歧义的小任务
- 只需要一个事实答案的查询
- 已经有明确正确性判据、不需要权衡的问题

下面这些也不归它管，各有专责——完整分工见 `SKILL.md` 的「本技能不做什么」，**那里是唯一定义点**：`skill-creator` 管技能目录与打包、`cross-review` 管多模型分发与外部复核、`skill-qa-tester` 管行为测试与回归、`agent-wiki` 管知识摄入与台账、`build-expert` 管高后果领域专家包。

---

## 三步上手

**1. 说清你拿不准的那件事**（不用结构化，原话就行）。

**2. 让它出简报。** 它会自动：判断这个问题值不值得这样想一遍 → 给问题分类 → 挑 1-3 个透镜 → 逐个交代改变了哪个决策 → 给反例和边界 → 指明下一步交给谁。

**3. 出稿前它会跑一次机检**，不通过就不许出稿：

```bash
python scripts/check_lens_brief.py <简报.md>
```

退出码：`0` 全过 ｜ `1` 有 FAIL（含零命中）｜ `2` 用法错。

## 它凭什么说自己有效

判据不是靠自觉。`scripts/check_lens_brief.py` 有 12 条机检（B1–B12），并且自带缺陷注入自检：

```bash
python scripts/check_lens_brief.py --selftest
python scripts/check_lens_brief.py --check-catalog
```

自检做两件事，缺一不算通过：

- **合法样本必须零误报**（不冤枉好稿）
- **12 个注入缺陷必须全部被捕获**（不放过坏稿）

只看退出码会被假绿骗过——这正是第 12 号透镜（M-12 机制上线前过双门槛）讲的事。

### 机检守不了什么

实测过一份**故意用错透镜**的简报：把故障态误判成建设期，得出「趁故障窗口整体重建」的结论——明显更差，但**它通过了全部 12 条机检**。

这不是 bug，是边界：B1–B12 守的是结构（八要素齐全、字段非占位、证伪条件存在），守不了「分类对不对、结论好不好」。内容质量要走独立评审——这也正是 P-08 那张透镜说的：结构一致性可外包，内容质量不能。

## 三条设计纪律

1. **没有决策增量的透镜一律撤下。** 写不出「原打算 X → 改为 Y」，说明它只是换个说法复述你已知的东西。
2. **边界密度 100%。** 每张卡都必须写「何时不该用」，没有例外。
3. **诚实账优先。** 来源是公开的就标 URL，是自撰的就标 `[自撰]`——不把自撰标成公开。

---

## 关于 `agent_created` 字段

`SKILL.md` 的 frontmatter 里有 `agent_created: true`。这是宿主平台（WorkBuddy / CodeBuddy）的管理字段，**不是 Agent Skills 开放规范字段**——规范只要求 `name` 与 `description`。删除它不影响本技能在任何兼容平台上使用。

---

## 版本

`SKILL.md` 的 `version` 与同名 git tag 对齐（如 `v1.0.0`）。版本号若只是写在文件里而没有对应 tag，使用者无法在 git 层锁定版本。变更记录见 `CHANGELOG.md`。
