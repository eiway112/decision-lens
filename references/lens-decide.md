# 透镜卷 · decide（选型 / 取舍 / 是否做）· 18 张

> **何时加载**：S1 分类后，决策类型维度命中「选型 / 取舍 / 是否做」时加载本卷。
> **字段纪律**：每张卡 6 个字段一次写全。`改变了哪个决策` 必须含转折（原打算 X → 改为 Y）；
> `什么证据会推翻` 与 `何时不该用` 不得留空或填占位。填不出即撤下该透镜。
> **来源标注**：`[公开]` 给出处 URL；`[自撰]` 表示本技能自撰判据、无外部来源。**不得把自撰标成公开。**

### D-01 · 入库判据：能否改变行为决策（源自 K01）

**主张**：一条知识值得入库，唯一判据是「它能否改变智能体在具体场景下的行为决策」。

**怎么用**
1. 写下这条知识会改变哪个具体场景下的哪个动作。
2. 指认不出场景 → 判不入库。
3. 能指认 → 写明适用边界后入库。

**改变了哪个决策**：原打算「这条写得不错，先存着」→ 改为「指不出它改变哪个动作，不存」。

**什么证据会推翻**：若一条从未改变过任何动作的知识，被证明在半年内避免了至少一次错误决策，则本判据过严。

**何时不该用**：存档 / 合规留痕场景不适用——那里的目的是留存，不是行为改变。

**互斥组**：存在性判据（D-01 / D-13 / D-12），同组最多选 1
**来源**：[公开] Farnam Street 心智模型（可用性判据同型）https://fs.blog/mental-models/

### D-02 · 知识与行动用相反的更新纪律（源自 K03）

**主张**：知识层只增不删（含失败与被否决记录），行动层每次变更须过验证门、失败即回滚。

**怎么用**
1. 先判这份资产属于知识层还是行动层。
2. 知识层：append-only，连错的都留。
3. 行动层：门控 + 失败即回滚到 last-known-good。

**改变了哪个决策**：原打算「把过时经验删掉保持整洁」→ 改为「知识层永不删，行动层失败即回滚」。

**什么证据会推翻**：若某知识层因保留错误经验而持续做出错误决策且无法纠正，则 append-only 需让位于纠错。

**何时不该用**：涉及个人隐私或需依法删除的内容。

**互斥组**：分层不对称（D-02 / D-05 / D-07），同组最多选 1
**来源**：[自撰]

### D-03 · 六成能力 + 显式介入点（源自 H01）

**主张**：准确率六成的工具不等于不可用——价值＝任务价值 × 使用频率 ×（1−缺陷损失率）。

**怎么用**
1. 估算三因子，别只看准确率。
2. 缺陷损失率高 → 在损失发生**之前**设强制人工介入点。
3. 介入点写进流程，不是「有空再看」。

**改变了哪个决策**：原打算「准确率才 60%，不能用」→ 改为「高频高价值 + 介入点前置＝可用」。

**什么证据会推翻**：若缺陷在下游不可被察觉（静默错误），介入点失效，本透镜不成立。

**何时不该用**：错误不可逆且不可检测的场景。

**互斥组**：无
**来源**：[公开] Anthropic, Building effective agents（human-in-the-loop 判据）https://www.anthropic.com/engineering/building-effective-agents

### D-04 · 上下文优势显性注入（源自 H02）

**主张**：人知道而模型不知道的背景，必须在动手前显性注入，不指望模型推断。

**怎么用**
1. 动手前列「用户知道哪些我不知道的事」。
2. 能自查查明的事实不问，只问查不到的。
3. 补齐后再动手。

**改变了哪个决策**：原打算「按字面需求直接开做」→ 改为「先补齐背景再动手」。

**什么证据会推翻**：若补齐背景后返工率无下降，说明瓶颈不在上下文而在需求本身。

**何时不该用**：纯执行型无歧义小任务；或背景已在同一会话中明确给出。

**互斥组**：无
**来源**：[自撰]；与 Anthropic 关于 workflow 中 human-in-the-loop 的建议同向 https://www.anthropic.com/engineering/building-effective-agents

### D-05 · 信任与闸门按「可逆性 × 可机验性」分层（源自 H04）

**主张**：不可逆且可机验的动作用强制闸门；开放且不可机验的判断给足上下文后信任模型。

**怎么用**
1. 判可逆性。2. 判可机验性。3. 四象限定位：闸门只管前者，信任只给后者。

**改变了哪个决策**：原打算「所有输出都过一遍自动检查」→ 改为「闸门只管不可逆可机验项，其余交信任」。

**什么证据会推翻**：若开放型判断经证明可被机器稳定判定、且误判代价高于闸门成本，则划分需重划。

**何时不该用**：两维都判不出来时——先补判据，不要用本透镜硬套。

**互斥组**：分层不对称（D-02 / D-05 / D-07），同组最多选 1
**来源**：[自撰]

### D-06 · 可见范围 ≠ 授权范围（源自 H07）

**主张**：可读范围与可改 / 可负责范围必须分开声明；二者不等宽时须写明。

**怎么用**
1. 派发时列出「可读什么」。2. 列出「可改什么、对什么负责」。3. 不等宽处显式标注。

**改变了哪个决策**：原打算「把资料全给它，让它自己看着办」→ 改为「可读全部，但只对 A 产出物负责」。

**什么证据会推翻**：若责任边界经实测不影响产出质量，则区分是形式主义。

**何时不该用**：单人单任务、无委派无并行。

**互斥组**：无
**来源**：[自撰]

### D-07 · LLM 只走优化路径，回落等价旧行为（源自 R04）

**主张**：LLM 参与的环节只能放优化路径，不能是正确性闸门；兜底必须等价于「这个环节不存在时的旧行为」。

**怎么用**
1. 先定性该环节是优化路径还是正确性路径。
2. 正确性路径不得放 LLM。
3. 降级绑唯一可判错误签名，回落必须留痕可见。

**改变了哪个决策**：原打算「用模型判断这一步是否通过」→ 改为「模型只做优化，通过与否由确定性规则判」。

**什么证据会推翻**：若模型在该环节的错误率经实测低于确定性规则，则本透镜不成立。

**何时不该用**：本就没有确定性旧行为可回落的全新环节——此时须先造一个。

**互斥组**：分层不对称（D-02 / D-05 / D-07），同组最多选 1
**来源**：[公开] Anthropic, Building effective agents https://www.anthropic.com/engineering/building-effective-agents

### D-08 · fail-closed 与装配期 fail fast（源自 R05）

**主张**：失败方向永远朝向更安全的一侧；危险组合在装配 / 启动期就拒绝，而不是运行期隐性损坏。

**怎么用**
1. 启动期做组合校验。2. 运行期任何不确定按失败处理。3. 不做「看起来能跑就放行」。

**改变了哪个决策**：原打算「参数不合法就按默认值继续」→ 改为「启动期直接拒绝启动」。

**什么证据会推翻**：若某组合经证明在真实运行中从不触发危险，则 fail fast 造成的是可用性损失而非安全收益。

**何时不该用**：降级路径本身更安全时——此时应降级，不是拒绝。

**互斥组**：角色分离（M-02 / M-05 / D-08），同组最多选 1
**来源**：[自撰]

### D-09 · 架构边界由会失败的测试强制（源自 R10）

**主张**：分层与边界靠会失败的测试守住，不靠文档约定。

**怎么用**
1. 为每条边界配一个失败用例。2. 边界变更须同步改测试。3. 文档只写意图，不写约束。

**改变了哪个决策**：原打算「在规范里写明分层要求」→ 改为「写一个违反即红的测试」。

**什么证据会推翻**：若该边界无法构造失败用例（本质不可测），则只能靠文档，本透镜不适用。

**何时不该用**：边界本身是价值判断而非事实判断（如「代码要易读」）。

**互斥组**：无
**来源**：[自撰]

### D-10 · 接口比实现长寿（源自 A03）

**主张**：把关键依赖虚拟化成稳定接口，为尚未想到的实现而设计——押注接口形状，不押当前实现。

**怎么用**
1. 识别三类易变依赖。2. 各自抽一层稳定接口。3. 接口形状先定，实现后适配。

**改变了哪个决策**：原打算「直接调这个库的最新 API」→ 改为「先定我需要的接口形状，再适配实现」。

**什么证据会推翻**：若该层在未来 2 个版本内确认不会更换，抽象即为净成本。

**何时不该用**：一次性脚本、明确不会复用的代码。

**互斥组**：无
**来源**：[自撰]

### D-11 · 确定性优先于智能（源自 A08）

**主张**：已有 API / DOM 等确定性链路时，换用 GUI 智能体不是升级而是降级。

**怎么用**
1. 选型前先审查前提：有没有 API、有没有 DOM、是不是只有一块屏幕。
2. 有确定性链路就用它。3. 视觉路线只作兜底。

**改变了哪个决策**：原打算「用视觉智能体更通用」→ 改为「有 API 就用 API，视觉是兜底」。

**什么证据会推翻**：若确定性链路的维护成本经证明高于视觉路线的错误率成本，结论反转。

**何时不该用**：确定性链路缺失或已废弃时。

**互斥组**：无
**来源**：[自撰]

---

### D-12 · 显式非目标清单（源自 A09）

**主张**：「不做什么」的清单与能力清单同等重要。

**怎么用**
1. 维护显式非目标清单。2. 死代码就地标注，不装作还活着。3. 每次新增能力同步更新非目标。

**改变了哪个决策**：原打算「先把功能都写上，边界用户自己会摸索」→ 改为「先写清不做什么」。

**什么证据会推翻**：若使用者经证明从不参考非目标清单（实测零消费），维护成本无回报。

**何时不该用**：探索期、边界尚未成形的原型阶段。

**互斥组**：存在性判据（D-01 / D-13 / D-12），同组最多选 1
**来源**：[公开] Farnam Street, Circle of Competence https://fs.blog/circle-of-competence/

### D-13 · 外部工具引入的存在性判据（源自 S06）

**主张**：评估外部工具的第一步是回答「本工作区哪一轮具体任务会调用它」——指认不出即判不引入。

**怎么用**
1. 指认具体调用任务。2. 指认不出 → 判不引入。3. 判否须同笔登记唯一的翻转前置事件。

**改变了哪个决策**：原打算「先装上试用一下」→ 改为「指认不出调用场景就不装」。

**什么证据会推翻**：若某工具在未指认场景的情况下被实际调用过，说明判据漏判。

**何时不该用**：纯学习 / 调研目的——但此时不算「引入」，须另行记账。

**互斥组**：存在性判据（D-01 / D-13 / D-12），同组最多选 1
**来源**：[自撰]

### D-14 · 冷启动最小闭环先进用户手（源自 S07）

**主张**：建设规模与需求确定性反挂钩——越不确定，最小闭环越小。

**怎么用**
1. 先定最小闭环范围（端到端能跑通的最小集合）。2. 进真实使用。3. 拿到信号后再扩。

**改变了哪个决策**：原打算「先搭完整架构再上线」→ 改为「先让最小闭环进用户手」。

**什么证据会推翻**：若某系统扩大规模后的返工成本经证明低于分批验证的协调成本，结论反转。

**何时不该用**：需求已高度确定且扩容成本极低时。

**互斥组**：无
**来源**：[自撰]

### D-15 · 宽构建窄交付（源自 S08）

**主张**：普通产物先在一条分支上整体建成，再由代码与产物揭示真实边界来拆分交付。

**怎么用**
1. 单分支整体建成。2. 按代码揭示的真实边界拆分。3. 分批交付。

**改变了哪个决策**：原打算「先开会定模块边界再开发」→ 改为「先做出来，让边界自己显现」。

**什么证据会推翻**：若真实边界无法从产物中读出（需额外判断），本透镜不适用。

**何时不该用**：交付物本身就是判据 / 治具 / 规范时——见 P-01。

**互斥组**：边界与停止（M-09 / P-01 / D-15 / D-16），同组最多选 1
**来源**：[自撰]

### D-16 · 结果判等时取简的一侧（源自 G02）

**主张**：结果判等时取更简的一侧，并把「删掉而结果不降」记为收益，而非需要自证清白的动作。

**怎么用**
1. 新增判据须两侧同取证：它比既有哪一条**少**、覆盖既有哪一条**未覆盖**的判定。
2. 指认不出即不新增。3. 判等则取简。

**改变了哪个决策**：原打算「为保险起见两条都留着」→ 改为「结果判等就删一条，记为收益」。

**什么证据会推翻**：若删掉后在未覆盖场景出现漏判，说明两条并不判等。

**何时不该用**：两条的失效条件不同——此时不是判等。

**互斥组**：边界与停止（M-09 / P-01 / D-15 / D-16），同组最多选 1
**来源**：[公开] Meadows, Leverage Points（simplification win）https://donellameadows.org/archives/leverage-points-places-to-intervene-in-a-system/

### D-17 · 补偿规则须标注补偿对象与失效判据（源自 G03）

**主张**：新增补偿型规则须同时写下它补偿哪个缺陷，并把失效判据绑定到「依赖升级事件」而非周期。

**怎么用**
1. 写清补偿对象（哪个缺陷）。2. 失效判据绑到依赖升级事件。3. 升级时回测该缺陷是否仍在。

**改变了哪个决策**：原打算「加个补丁解决这个问题」→ 改为「先写明它补的是哪个缺陷、什么时候该撤」。

**什么证据会推翻**：若被补偿的缺陷在依赖升级后经实测仍存在，则失效判据未触发，规则继续有效。

**何时不该用**：一次性临时修补——但须就地标注为临时。

**互斥组**：衰减与失效（D-17 / P-09 / M-10），同组最多选 1
**来源**：[自撰]

### D-18 · 知识规则不得取得与用户当前指令同等的权限（源自 G06）

**主张**：规则「已落地」不等于用户授权本次提交或扩大任务范围；冲突时以本轮授权为准并记录。

**怎么用**
1. 执行前区分「规则要求」与「本轮授权」。2. 冲突以本轮授权为准。3. 记录冲突供事后审。

**改变了哪个决策**：原打算「规范里写了要做，所以直接做」→ 改为「先看这一轮用户授权范围」。

**什么证据会推翻**：若用户已就该规则给出覆盖本轮的明确长期授权，则不构成冲突。

**何时不该用**：用户已就该规则给出长期授权时。

**互斥组**：无
**来源**：[自撰]
